# ULTARI

사진 파일에 남은 촬영 흔적을 **브라우저 안에서** 측정하고, 그 측정값을 근거로 등급을 발급합니다.

> AI를 안 썼다는 걸 증명하는 게 아닙니다. 사람이 만들었다는 흔적을 남기는 겁니다.

하지 않는 주장: AI 이미지 탐지, AI 학습 차단, 100% 정확도.

---

## 타협 불가 원칙

**간단 검사에서 이미지는 서버로 전송되지 않습니다.** 검사 코드(`src/verify/*`, `grade.js`,
`score.js`, `watermark.js`)에 `fetch`, `XMLHttpRequest`, `WebSocket`, `form action`이 하나도
없습니다. 확인하려면 개발자 도구의 네트워크 탭을 켜고 간단 검사를 해 보십시오.

**상세 검사는 다릅니다.** 사람이 사진을 보려면 파일이 사람에게 가야 합니다. 그래서 상세 검사
신청 버튼을 누를 때 사진 원본이 서버로 올라갑니다. 네트워크를 쓰는 코드는 `src/review.js`
하나뿐이고, 그 버튼 뒤에서만 호출됩니다. 무엇을 받고 언제 지우는지는 `/privacy` 9항에 있습니다.

이 경계를 흐리지 마십시오. "사진은 전송되지 않는다"를 무조건적으로 다시 적으면 거짓이 됩니다.

```bash

```

`vite.config.js`의 `cleanUrls` 플러그인이 개발/프리뷰 서버에서 `/how` → `how.html`을 처리합니다.
Cloudflare Pages는 같은 규칙을 기본으로 제공합니다.

## 상세 검사 접수 — 서버 설정

상세 검사만 서버를 씁니다. Cloudflare Pages Functions(`functions/api/*`)와 KV 하나,
관리 키 하나가 필요합니다. **대시보드에서 직접 만들어 연결해야 합니다.**

| 종류 | 바인딩 이름 | 쓰임 |
|---|---|---|
| KV 네임스페이스 | `ULTARI_APPS` | 접수 기록, 대기 색인, 사진 원본 |
| 환경 변수 (시크릿) | `ULTARI_ADMIN_KEY` | 심사자용 키. 상태 변경과 사진 조회 |

사진도 KV에 넣습니다. R2가 더 맞는 자리지만 Cloudflare가 R2에 결제수단 등록을 요구합니다 —
무료 한도 안에서만 써도 카드를 걸어야 합니다. KV 값 한도는 25MiB이고 업로드 상한을 20MB로
잡았으니 심사 대기열 분량은 충분합니다. 분량이 늘면 `photoKey()`가 가리키는 곳만 R2로 바꾸면
됩니다.

Pages → 프로젝트 → Settings → Bindings에서 추가합니다. KV가 없으면 접수 API가 503으로
답하고, 빠진 바인딩 이름은 로그에만 남습니다(방문자에게 내부 이름을 보이지 않습니다).
간단 검사는 영향받지 않습니다.

### 경로

| 메서드 | 경로 | 하는 일 |
|---|---|---|
| POST | `/api/apply` | 사진 + 연락처 + 조회 비밀번호 + 상황을 받아 접수번호 발급 |
| POST | `/api/status` | `{contact, password}` 또는 `{id, token}`으로 현황 반환 |
| GET | `/api/admin` | 대기 건수만 반환 (공개) |
| GET | `/api/admin?list=1` | 접수 목록 전체. 관리 키 필요 (비밀번호 해시는 제외) |
| GET | `/api/admin?photo=ID` | 심사자가 사진을 내려받음. 관리 키 필요 |
| POST | `/api/admin` | 상태 변경, 심사 판단 저장, 되돌리기, 보관 만료 삭제. 관리 키 필요 |

상태는 `received` → `reviewing` → `done`이고 `waiting`(추가 자료 대기)과 `rejected`도 있습니다.
화면에는 **신청 → 심사 중 → 결과 발표** 세 칸으로 보입니다.

### 조회 자격

신청할 때 **연락처와 비밀번호**를 받고, 조회도 그 둘로 합니다. 32자 열쇠를 받아 적게 하는
방식은 너무 번거로웠습니다. 열쇠는 여전히 발급하지만 화면에 보이지 않고, 신청한 브라우저가
비밀번호 없이 자기 접수를 여는 데만 씁니다(localStorage).

비밀번호는 PBKDF2-SHA256 20,000회로 늘려 해시만 저장합니다. 반복 횟수는 요청당 CPU 예산에서
나온 값입니다 — workerd에서 30,000회가 7ms로 측정됐고 Workers 무료 플랜의 요청당 CPU는
10ms입니다. 소금은 연락처에서 결정론적으로 만듭니다. 접수마다 무작위 소금을 쓰면 한 번
조회할 때 접수 수만큼 PBKDF2를 돌려야 해서 예산을 넘습니다. 대신 특정 메일 주소를 겨냥한
사전 계산이 가능해지는 것이 값이고, 그 비용은 여전히 PBKDF2가 지배합니다.

연락처는 남이 알 수 있는 값이므로 틀린 시도를 셉니다. 같은 연락처로 10번 틀리면 15분간
막습니다(`fail:` 키, KV TTL). 조회 응답에는 사진도 연락처도 들어가지 않습니다.

비밀은 GET 쿼리로 보내지 않습니다. 주소는 접속 기록에 남습니다.

### 심사 판단

사람이 무엇을 보고 판단했는지 기록합니다. 기준 목록은 `src/review-criteria.js` 한 곳에
있고 심사 콘솔과 서버가 같은 것을 씁니다 — 두 곳이 따로 갖고 있으면 화면에서 고른 기준이
서버에서 조용히 버려집니다.

기준마다 `확인됨` / `어긋남` 둘 중 하나를 기록하고, 고르지 않은 것은 저장하지 않습니다
(적지 않은 것과 같습니다). `POST /api/admin`이 받는 것:

```jsonc
{
  "id": "ABCD-2345",
  "status": "done",
  "awarded": 2,                       // 발급 등급 3·2·1 또는 null(등급 없음)
  "checks": { "original": "pass", "siblings": "fail" },
  "result": "신청자에게 보일 문장",     // done·rejected에는 필수
  "note": "이력에만 남는 메모"
}
```

`done`이나 `rejected`로 옮길 때 `result`가 비어 있으면 서버가 거절합니다. 결과를 알리는
상태인데 신청자가 읽을 문장이 없으면 등급은 근거 없는 숫자가 됩니다. 1등급은 센서 지문
대조가 확인돼야 하고, 화면이 누르기 전에 알려 주지만 막지는 않습니다 — 판단은 심사자가
합니다.

`{ "id": "...", "action": "revert" }`는 직전 상태로 되돌립니다. 바꾸기 전 상태를 레코드에
쌓아 두고(`undo`, 최근 20개) 하나씩 되짚습니다. 되돌리면 상태·등급·기준·결과문이 함께
돌아가고, 완료였던 건은 대기 색인에 다시 들어갑니다(그래야 뒷사람 예상일이 맞습니다).

발급 등급과 기준별 판단은 **신청자 화면에도** 그대로 나옵니다.

### 발급물 — 인증서와 인증 마크

사람 심사가 끝나고 등급이 나온 접수에는 조회 화면에 발급물 칸이 생깁니다.

- **인증서**(`src/certificate.js`) — 등급, 접수번호, 원본 지문, 기준별 판단, 소견을 담은
  A4 비율 PNG. Canvas로 그 자리에서 그립니다. 보장하지 않는 것도 같은 종이에 적습니다 —
  근거 없이 등급만 적힌 종이는 아무것도 증명하지 않습니다.
- **인증 마크** — 발급된 등급으로 새깁니다. 원본 파일이 있어야 하므로 조회 화면에서 파일을
  한 번 더 받고, **심사받은 파일과 지문이 같은지 먼저 대조합니다.** 다른 사진에 마크를 새겨
  주면 마크가 거짓이 됩니다. 이 파일도 서버로 가지 않습니다.

### 심사 화면 — `/admin`

심사자용 페이지입니다. `noindex`이고 메뉴에서 링크하지 않으므로 주소를 알아야 들어옵니다.
관리 키를 넣으면 목록이 열리고, 카드마다 **사진이 바로 보입니다**(8MB 이하는 자동, 그보다
크면 눌러서). 사진은 관리 키를 헤더로 보내야 받을 수 있어 `img src`로 걸 수 없으므로 받아서
objectURL로 붙이고, 원본 내려받기도 같은 것을 씁니다. 그 아래에 심사 판단(기준 9개) ·
발급 등급 · 결과문 · 상태 이동 · 되돌리기가 있습니다.

지우는 버튼은 두 개이고 하는 일이 다릅니다.

| 버튼 | 지우는 것 | 남는 것 | 쓰는 때 |
|---|---|---|---|
| 보관 만료 정리 | 사진, 연락처, 촬영 상황 | 접수번호, 등급, 심사 이력 | 완료 후 90일이 지난 건. `/privacy`의 약속을 지키는 수단입니다 |
| 접수 삭제 | 전부 — 사진, 기록, 대기 색인, 연락처 색인 | 없음 | 잘못 들어온 접수, 신청자가 지워 달라고 한 경우 |

정리는 심사 기록을 남기므로 나중에 "그 접수가 몇 등급이었나"를 답할 수 있고, 삭제는 그것까지
없애므로 신청자도 조회할 수 없게 됩니다. **심사 완료 · 결과 발표** 버튼
하나가 기준·등급·결과문·상태를 한 번에 넘깁니다. 상태만 옮기는 버튼도 적어 둔 판단을 함께
저장합니다 — 타이핑을 버리지 않습니다. 열쇠는 `sessionStorage`에만 두므로 탭을 닫으면
사라집니다.

목록은 `index:open`이 아니라 `app:` 접두어 키를 훑습니다. 색인은 끝난 건을 빼기 때문에
그것만 보면 완료된 접수가 보이지 않습니다.

신청하신 분이 보는 화면은 따로입니다 — 검증 화면의 **상세 검사 진행 현황 조회**(접수번호 +
조회 열쇠). 조회 응답에는 사진도 연락처도 들어가지 않습니다. 열쇠가 새도 사진까지 새지
않게 하려고 그렇게 만들었습니다.

**AI 생성 기록이 있는 파일은 접수하지 않습니다.** C2PA에 `trainedAlgorithmicMedia`가 적혀 있으면
화면에서 신청 폼을 내리고, `/api/apply`도 422 `declared-ai`로 돌려보냅니다. 두 곳이 같은
`scanProvenance()`를 쓰므로 판단이 갈리지 않습니다. 화면만 막으면 요청을 직접 보내는 것으로
지나갑니다.

막는 것은 **파일이 스스로 선언한 경우뿐**입니다. `판정 불가`, `보류`, `카메라 쪽 0건`은 막지
않습니다. 메신저를 거친 실제 사진도 그렇게 나오고, 그런 사진이야말로 사람 심사가 필요합니다.

```bash
# 사진 받아 보기
curl -H "x-ultari-admin: $ULTARI_ADMIN_KEY"   "https://ultari.pages.dev/api/admin?photo=ABCD-2345" -o ABCD-2345.jpg

# 심사 착수
curl -X POST https://ultari.pages.dev/api/admin   -H "x-ultari-admin: $ULTARI_ADMIN_KEY" -H "content-type: application/json"   -d '{"id":"ABCD-2345","status":"reviewing","note":"담당자 배정"}'

# 완료
curl -X POST https://ultari.pages.dev/api/admin   -H "x-ultari-admin: $ULTARI_ADMIN_KEY" -H "content-type: application/json"   -d '{"id":"ABCD-2345","status":"done","result":"2등급 발급"}'
```

```bash
# 보관 기간(완료 후 90일)이 끝난 접수 — 사진과 연락처를 지웁니다
curl -X POST https://ultari.pages.dev/api/admin   -H "x-ultari-admin: $ULTARI_ADMIN_KEY" -H "content-type: application/json"   -d '{"id":"ABCD-2345","action":"purge"}'
```

`/privacy`에 "완료 후 90일에 지운다"고 적어 두었으므로 지울 수단이 없으면 그 문장이 거짓이
됩니다. 그래서 삭제를 같이 만들었습니다. 아직 자동으로 돌지는 않으니 손으로 부르셔야 합니다.

조회 열쇠는 접수 응답에 한 번만 나가고 서버에는 SHA-256 해시만 남습니다. 재발급이 불가능한
것은 의도된 것이고, 접수번호가 새어도 남의 신청을 열 수 없게 하기 위한 것입니다.

## 배포 전에 반드시 고쳐야 하는 것

`src/queue.js` 한 파일입니다.

```js
export const CONTACT = 'hello@ultari.kr';   // ← 실제로 받을 수 있는 주소로
export const REVIEW_QUEUE = { updatedAt: '2026-09-11', grade2: 0, grade1: 0, archive: 0 };
```

- `CONTACT`는 자리표시자입니다. 실제 주소로 바꾸십시오. 심사 접수, 아카이브 접수, 피드백이
  모두 이 주소 하나를 씁니다.
- `REVIEW_QUEUE`의 숫자는 `/api/admin` 호출이 실패했을 때 쓰는 대체값입니다. 실제 대기
  건수는 서버에서 옵니다. 0건이면 0건이라고 씁니다. 진위를 파는 서비스가 대기열을 부풀리면
  그 순간 팔 물건이 없어집니다.

### 두 개의 투입구

첫 화면에 파일을 넣는 곳이 둘입니다.

| | 간단 검사 | 상세 검사 |
|---|---|---|
| 걸리는 시간 | 30초 | 며칠~몇 주 |
| 누가 | 기계 | 기계 + 사람 |
| 최대 | 3등급 | 1등급 |
| 결과 | 즉시 판정 + 인증 마크 | 같은 측정 + 사람 심사 신청서 |

둘 다 브라우저 안에서 같은 측정을 합니다. 상세 검사는 그 결과를 사람이 읽을 신청서로
만들어 주고, 접수는 `/api/apply`가 받습니다. **측정 자체는 어느 쪽에서도 파일을 보내지
않습니다.** 파일이 올라가는 것은 상세 검사 신청 버튼과 아카이브 등록 버튼을 누른 뒤이고,
그 자리에 그렇게 적어 두었습니다.

### 검증 화면은 걸음 넷입니다

한 문서에 고르는 칸·진행·결과를 차례로 쌓아 두면 결과를 보려고 지나온 것을 지나쳐
내려가야 합니다. 그래서 같은 자리에서 갈아 끼웁니다.

| 걸음 | 무엇 | 되돌아가면 |
|---|---|---|
| 1 / 4 | 고르기 — 견본 두 장과 투입구 둘 | (브라우저에 맡깁니다) |
| 2 / 4 | 검사 — 진행률과 9단계 | 고르기 |
| 3 / 4 | 결과 — 판정, 숫자 하나, 접힌 근거 | 고르기 |
| 4 / 4 | 받기 — 인증 마크와 아카이브 등록 | 결과 |

되돌아갈 자리는 화면 위 막대에 있고, **브라우저와 기기의 뒤로가기도 같은 곳으로 갑니다**
(`history.pushState` + `popstate`). 결과 화면에서 뒤로를 누른 사람이 사이트 밖으로 튕겨
나가면 그 사람은 돌아오지 않습니다. 재는 중에는 걸음이 움직이지 않고, 뒤로 신호가 와도
칸을 도로 밀어 넣습니다.

고르는 걸음이 아닐 때는 페이지 머리말과 페이지 아래 설명 칸(`[data-extra]`)을 접습니다.
결과를 보고 있는 사람에게 "올려 보시면 바로 나옵니다"는 더 알려 주는 것이 없습니다.

### 결과 화면에는 숫자를 하나만 답니다

판정이 통과면 **촬영 흔적**을, 그 밖이면 **AI 쪽 환산**(`100 - trace`)을 크게 적습니다.
두 값은 서로의 나머지라 같이 걸어 둘 이유가 없습니다.

근거는 지우지 않고 접습니다 — `AI 판별 기준`, `환산 수치는 어떻게 나왔나`,
`인증 마크 발급 조건`, `측정값 전체 보기`가 전부 닫힌 채로 붙어 있습니다. 펼쳐 두면
결과보다 표가 먼저 읽히고, 처음 온 사람은 무엇을 받았는지 모른 채 스크롤합니다.

**AI 쪽 환산은 "AI가 만들었다"는 확률이 아닙니다.** 촬영 흔적이 얼마나 안 남아 있는지를
잰 값이고, 그 문장을 숫자 바로 아래 같은 칸에 적습니다. 실제로 이 숫자는 뒤집히기도
합니다 — 견본으로 둔 AI 생성 풍경은 비네팅·색수차·초점 연속성·압축 격자를 모두 통과해
`AI 쪽 35%`가 나오고, 메신저를 거치지 않은 아이폰 원본은 압축 격자가 구역별로 달라
`촬영 흔적 83%`에 그칩니다. 재는 것이 "카메라를 지난 흔적"이지 "생성물인가"가 아니기
때문입니다.

### 진행 상황을 보여 주는 일

검사가 돌아가는 동안 9단계 목록이 완료/진행 중으로 표시되고, 끝나면
`검사 완료 · 9단계 · 0.8초`가 그대로 남습니다. 진행이 안 보이면 사용자는 업로드가 안 된
줄 압니다. 같은 자리에 "이 기기에서 계산 중입니다. 업로드가 아닙니다"를 붙여 두었고,
끝나면 과거형으로 바뀝니다.

### 인증 마크

3등급을 받으면 결과 화면 끝에 받으러 가는 칸이 서고, 한 번 누르면 **마크가 새겨진
미리보기가 이미 그려진 채로** 받기 걸음이 열립니다. 마크에는 울타리 도형, 등급,
원본 지문 앞자리가 들어갑니다.

- **위치 선택** — 좌측 하단(기본) / 우측 하단 / 좌측 상단 / 우측 상단. 바꾸면 미리보기가
  즉시 다시 그려집니다.
- **마크 넣은 사진 내려받기** — 미리보기는 긴 변 1100으로 줄여 그리고, 내려받기는 그때
  원본 해상도로 다시 그립니다. 축소본을 원본인 척 내주지 않습니다.
- **마크만 내려받기** — 명판만 담은 투명 PNG. 크기는 그 사진에 얹었을 때와 같으므로
  편집 프로그램에서 1:1로 올리시면 됩니다.

합성은 Canvas로 브라우저 안에서 하고, 명판 높이는 짧은 변의 5~6%로 잡았습니다.
마크를 넣으면 파일의 바이트가 달라져 지문도 달라지므로 마크 안에 원본 지문을 같이 새기고,
그 사실을 화면에도 적습니다.

### 받기 걸음 — 마크와 계좌

검증이 끝난 자리에서 받는 것까지 이어집니다. 결과만 보여 주고 끝내면 무엇을 받는
서비스인지가 화면에 없습니다.

1. **인증 마크** — 위치를 고르고 내려받습니다. 브라우저 안에서 그립니다.
2. **아카이브 등록** — 연락처와 조회 비밀번호를 받아 `/api/apply`에 `grade=3`으로
   보냅니다. 심사 신청과 같은 접수 경로를 씁니다 — 경로를 하나 더 두면 접수번호 체계와
   대기 색인이 갈립니다.

**등록 여부를 고르게 하지 않습니다.** 검증한 것은 모두 등록됩니다. 화면에 고르개가 없고
서버도 `archive = true`로 고정합니다. 거두실 때는 연락처로 말씀하시면 지웁니다 — 접수
순간에 고르게 하는 것보다 그쪽이 되돌리기 쉽습니다.

**배분받을 계좌는 받지 않습니다.** 로그인 기능을 붙인 뒤에 계정에서 받습니다. 지금
받아 두면 로그인이 생겼을 때 어느 계정의 것인지 이어 붙일 수가 없고, 쓸 데도 없는 금융
정보를 들고 있게 됩니다. 화면에는 그 사실을 적은 줄(`.later-note`)만 둡니다.

파일이 올라가는 것은 등록 버튼을 누른 뒤입니다. 자동으로 올리지 않습니다 — "등록이
자동"이라는 것은 *고를 것이 없다*는 뜻이지 *동의 없이 보낸다*는 뜻이 아닙니다.

### 시험 운영 띠

`site.js`의 `paintTrialBar()`가 모든 페이지 **화면 아래에** 고정된 띠를 붙입니다.
판매도 배분도 이루어진 적이 없고 계좌를 받지 않는다는 사실을 계속 보이게 하는 것입니다.

위가 아니라 아래인 이유는 배치입니다. 랜딩의 상단 바가 `position: fixed`이고 화면들이
`100svh`로 붙어 있어서, 위에 끼우면 그 높이만큼 전부 어긋납니다. 아래에 두면 어느
페이지의 배치도 건드리지 않습니다. `.site-foot`에 그만큼 `padding-bottom`을 줍니다.

띠는 닫히지 않습니다. 시험 중이라는 사실은 한 번 읽고 넘길 것이 아니라 계속 사실입니다.

### 파일 선택이 되지 않던 문제

처음 구현은 드롭존에 클릭 핸들러를 걸고 그 안에서 `input.click()`을 불렀습니다. 이렇게 하면
프로그램이 만든 클릭이 다시 드롭존으로 버블링돼 클릭 한 번에 이벤트가 두 번 도달하고,
브라우저에 따라(특히 iOS Safari) 파일 선택창이 아예 열리지 않습니다.

지금은 숨긴 `<input>`을 `<label for>` **바로 앞**에 두고 브라우저의 기본 동작에 맡깁니다.
JS는 `change`와 드래그 앤 드롭만 듣습니다. 헤드리스 Chromium에서 클릭당 선택창이 정확히
1회 열리는 것과 키보드로도 열리는 것을 확인했습니다.

`src/verify/pixels.js`와 `src/queue.js`는 명세의 파일 목록에 없지만 추가했습니다.
전자는 여섯 모듈이 같은 디코딩 결과를 나눠 쓰기 위한 것이고(원본 2400만 화소를 통째로
ImageData로 올리면 96MB가 필요합니다), 후자는 대기 건수와 접수처가 두 페이지에서 쓰여
단일 출처가 필요하기 때문입니다.

### 왜 해상도를 둘로 나누는가

노이즈, JPEG 8×8 격자, 색수차, 모아레는 **원본 배율에서만** 살아남습니다. 축소하면 인접 화소가
평균되면서 재려던 신호가 사라집니다. 반면 비네팅과 초점 분포는 화면 전체의 저주파 특성이라
축소본이 더 안정적입니다. 그래서 `pixels.js`가 3×3 위치의 원본 배율 타일(512×512, 8의 배수
정렬)과 긴 변 1280의 축소본을 함께 만듭니다.

## 판정 규칙

결과는 셋뿐입니다. **“AI입니다”나 “AI 의심”은 어떤 경우에도 출력하지 않습니다.**

| 결과 | 조건 |
|---|---|
| 3등급 발급 | 촬영 정보가 있고, 정합성 모순이 없음 |
| 판정 불가 | EXIF 없음 / 촬영 기기 없음 / 촬영 시각 없음 / 화소 부족 |
| 보류 | 정합성 모순 1건 이상, 또는 약한 신호 2건 이상 |

- **정합성 모순** (`consistency.js`): ISO 대 실측 노이즈 불일치, 노이즈-신호 역전, 노이즈-신호 균일

노이즈-신호 기울기를 낼 때 σ가 0.15 아래인 휘도 구간은 빼고 맞춥니다. 스튜디오 배경지,
보정한 피부, 날아간 하늘은 센서 반응이 아니라 평탄하게 밀린 면입니다. 증명사진 한 장에서
가장 밝은 구간이 패치 3189개에 σ=0.07이었고, 그 구간 하나가 상관을 -0.74까지 끌어내려
실제 사진이 모순으로 찍혔습니다. 재지 못한 것을 0으로 세면 없는 기울기가 생깁니다.
- **약한 신호**: 렌즈 흔적 없음, 초점 불연속, 압축 격자 영역별 편차

약한 신호는 혼자서는 판정을 바꾸지 않습니다. 하늘과 나뭇잎만으로도 값이 크게 벌어지고,
카메라 내 보정과 크롭이 렌즈 흔적을 지우기 때문입니다. 오탐으로 창작자를 모욕하는 대가가
미탐보다 큽니다. 이 조합 규칙은 `src/grade.js`의 `T.softSignalsForHold` 한 줄입니다.

화면 재촬영 신호(모아레, 평면성)는 **등급을 깎지 않습니다.** 기계가 확정할 수 없는 자리라
표시만 하고 2등급 심사로 넘깁니다.

### 합격선

각 모듈 상단의 `const T = { ... }`에 모여 있습니다. **화면에 노출하지 않습니다.** 측정값과
판정 단어는 전부 공개하되, 합격선을 공개하면 그 선에 딱 맞춘 파일을 만드는 일이 쉬워집니다.

## 검증 방법

브라우저가 없는 환경에서도 측정 로직을 확인할 수 있도록, 합성 이미지로 각 모듈을 돌려
값을 대조했습니다. 확인한 것:

- 포아송 노이즈를 넣은 화면에서 휘도 8구간의 σ가 단조 증가하고 상관이 +1.00
- 노이즈를 평탄하게 만들면 상대 폭 0.02로 떨어지고 균일 플래그가 섬
- 비네팅 0.3을 넣으면 코너/중앙 0.77, 넣지 않으면 0.97
- 색수차를 넣으면 0.5~0.8px, 넣지 않으면 0.00px
- 8×8 블록 DC 오차를 넣으면 격자 세기 1.31, 3픽셀 어긋난 두 번째 격자를 얹으면 2차 피크 1.32
- 왼쪽 1/3에만 격자를 빼면 격자 약한 구역 3개가 잡힘
- 모아레를 주입했을 때만 주파수 피크가 검출됨

실제 브라우저(Chromium)에서 Canvas로 JPEG을 인코딩하고 EXIF를 붙인 파일로
세 가지 판정 경로를 모두 확인했고, 검증 중 발생한 네트워크 요청에 GET 이외는 없었습니다.

## AdSense

- 광고 자리는 `.ad-slot`으로 레이아웃에만 잡혀 있습니다. **스크립트는 넣지 않았습니다.**
  승인 전에 넣으면 의미가 없습니다.
- `/privacy`와 `/terms`가 있고, 간단 검사에서 이미지가 전송되지 않는다는 사실과 상세 검사에서
  무엇을 받아 언제 지우는지를 나눠 적었습니다.
- `/articles/`에 글 3편이 있고, `/archive`와 `/roadmap`도 읽을 내용이 있는 페이지입니다.
  도구 하나만 있는 사이트는 “가치가 낮은 콘텐츠”로 거절될 가능성이 높습니다.
  **글이 더 쌓이기 전에는 신청하지 않는 편이 낫습니다.**
- 중복 페이지를 만들지 않았습니다. 탐색은 6개 항목 한 줄입니다.

## 알려진 한계 (구현 쪽)

- RAW와 일부 HEIC는 브라우저가 디코딩하지 못합니다. 서버가 없으므로 변환해 줄 수도 없습니다.
- 노이즈 측정은 JPEG 저장 화질에 크게 영향을 받습니다. 화질을 낮춰 저장하면 노이즈가 깎입니다.
- 압축 격자 추정은 휴리스틱입니다. 양자화 테이블을 직접 읽지 않습니다.
- 센서 지문(1등급)은 구현돼 있지 않습니다. 접수만 받습니다.
- 오리지널 아카이브는 접수만 받습니다. 판매도 배분도 이루어진 적이 없고, 그래서 배분 비율을
  숫자로 적지 않았습니다.
- 인증 마크는 사진 위에 그린 그림입니다. 지우거나 흉내 낼 수 있습니다. 마크가 아니라
  마크에 적힌 지문이 대조의 근거입니다.

검증 자체의 한계는 `/limits`에 따로 적어 두었습니다. 그쪽이 더 중요합니다.
